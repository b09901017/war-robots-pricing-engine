# War Robots 禮包比價與基準單價推算

給手遊《War Robots》玩家用的商城禮包比價工具。記錄你看過的禮包（售價 + 內容物），
它會自動反解出每一種物品的「基準單價」，然後告訴你新看到的禮包到底值不值得買。

整個 App 跑在 **Google Apps Script** 上，**Google 試算表就是資料庫**。免伺服器、免費、
手機和電腦開同一個網址就能用，資料也天生就在你自己的試算表裡。

---

## 它在解什麼問題

商城從來不會告訴你「1 顆金幣值多少錢」。但每一筆禮包其實都是一條方程式：

```
售價 ≈ 數量₁ × 單價₁ + 數量₂ × 單價₂ + …
```

記了十幾筆之後，這些方程式疊起來就是一個超定線性系統，可以把單價解出來。
單價不可能是負數，所以用**帶 ridge 正則化的非負最小平方（NNLS）**求解。

實作上有三個關鍵處理，少一個結果就會歪掉：

| 處理 | 為什麼需要 |
|---|---|
| **相對誤差加權** | 直接對「元」做最小平方的話，一筆 3290 元的禮包會壓過十筆 90 元的。每列除以該包售價後，貴包便宜包才有同等發言權。 |
| **欄位正規化** | 銀幣一次給 250 萬、終極資料卡一次給 1 張，量級差了八個數量級。把每個欄位縮成單位長度求解，最後再還原。 |
| **Bootstrap 區間** | 只出現在一兩包裡的稀有物品，點估計幾乎沒有意義。重抽禮包重解 240 次，用分位數給出「可能區間」而不是一個假裝很確定的數字。 |

引擎跑在**瀏覽器端**，所以改一個數字就立刻重算，不必等伺服器往返。
Apps Script 只負責試算表的讀寫。

## 正式架設（約 5 分鐘）

### 1. 建立試算表與指令碼

1. 開一個新的 Google 試算表，取名例如「War Robots 禮包」。
2. 選單 **擴充功能 → Apps Script**，會開啟一個綁定在這張試算表上的指令碼專案。
3. 記下網址列裡的 `scriptId`（`https://script.google.com/.../projects/<scriptId>/edit`）。

### 2. 推送程式碼

```bash
npm install
npx clasp login

cp .clasp.json.example .clasp.json
# 編輯 .clasp.json，把 scriptId 填進去

npm run push
```

> `npm run push` 會先跑 `tools/build.js` 把 `src/` 組裝成 `dist/`，再 `clasp push`。
> 不想用 clasp 的話，也可以手動把 `dist/` 裡的檔案一個個貼進 Apps Script 編輯器
> （`.gs` 貼成指令碼檔、`ui/*.html` 貼成 HTML 檔，檔名要完全一致，含 `ui/` 前綴）。

### 3. 初始化工作表

回到試算表，**重新整理頁面**，上方會多出「War Robots 禮包比價」選單。

點 **初始化 / 修復工作表**。第一次會要求授權，照著走完即可。
它會建立四張工作表：

| 工作表 | 內容 |
|---|---|
| `禮包` | 你的禮包紀錄。每個物品一欄的寬表，可以直接在試算表上編輯。 |
| `單價看板` | 算出來的基準單價、區間、信心度。最後一欄 `鎖定單價` 是**你可以填的輸入**。 |
| `設定` | 推算參數。 |
| `試算紀錄` | 你按下「存進試算紀錄」時累積的試算結果。 |

想先試用的話，再點一次 **載入範例資料**。

### 4. 部署成網頁 App

在 Apps Script 編輯器裡：**部署 → 新增部署作業 → 類型選「網頁應用程式」**

- 執行身分：**我**
- 存取權限：**只有我自己**（預設值，最安全）

部署後拿到的網址就是你的 App。手機加到主畫面就跟原生 App 一樣。

> 存取權限預設是「只有我自己」，也就是只有你的 Google 帳號打得開。
> 如果改成「知道連結的任何人」，**任何拿到網址的人都能讀寫你的試算表**，請斟酌。

也可以不部署，直接用選單的 **開啟比價面板**，在試算表裡以對話框開啟同一份介面。

## 怎麼用

### 記錄禮包
「禮包」分頁 → 新增。物品點丸子選，數量和售價用數字鍵盤輸入（電腦上也可以直接打實體鍵盤）。

### 看單價
「看板」分頁。每一列是一種物品：

- **大數字** 是基準單價（1 單位值多少台幣）
- **淺色橫條** 是 80% 可能區間，中間的直線是點估計。橫條越寬代表越不確定
- **信心度標籤** 綜合「出現在幾包裡」和「區間有多寬」
- 只出現在 1 包裡、或被解成 0 的物品，會直接寫明原因，不會假裝那是行情

橫條的橫軸是「相對於這個物品自己的點估計，從 0 到 2 倍」——
所以銀幣和終極資料卡雖然差了八個數量級，還是能在同一個看板上比較「有多不確定」。

### 試算新禮包
「試算」分頁，輸入售價和內容物，會即時算出：

- **性價比指數** = 理論價值 ÷ 售價，以及它自己的可能區間
- **評價**（超值 / 划算 / 正常行情 / 偏貴 / 很貴）
- 這包在你記錄過的所有禮包裡排第幾
- 價值是由哪些物品撐起來的

「正常行情」的寬度不是拍腦袋訂的，而是**跟著模型自己的平均誤差走**。
如果模型連歷史禮包都有 15% 的誤差，那 1.10 倍就分辨不出是划算還是雜訊，不該說它超值。

### 鎖定單價（讓結果收斂的最有效手段）
「設定」分頁，對任何物品填入你有把握的單價，它就會被當成已知值從售價裡先扣掉，
其餘物品再去解剩下的部分。稀有物品估不準的時候，先鎖幾個你確定的常見物品，
整體結果會立刻穩下來。

## 常見狀況

**「有物品被解成 0 元」**
代表它在資料裡總是跟別的東西綁在一起出現，方程式分不出它自己的貢獻。
記一筆「只含它」或「搭配組合不同」的禮包就會解開。

**「待解物品比禮包筆數還多」**
方程式不夠。繼續累積禮包，或鎖定幾個有把握的單價。

**「某個物品的區間寬得離譜」**
它出現的次數太少，或總是和另一個物品等比例出現（共線）。這是誠實的結果，不是 bug。

**手動改了試算表之後 App 沒更新**
重新整理 App 頁面即可。資料的唯一真實來源就是試算表。

## 開發

```bash
npm test          # 演算法測試（node --test，不需要任何相依套件）
npm run preview   # 產生離線預覽版
npm run serve     # 產生並起一個本機伺服器
npm run build     # 只組裝 dist/
npm run push      # 組裝 + clasp push
```

### 專案結構

```
src/
  lib/            純 JS 演算法，同時被三個環境載入（見下）
    catalog.js      物品目錄、數字格式化
    linalg.js       NNLS、Cholesky、bootstrap 亂數
    solver.js       基準單價推算引擎
    evaluate.js     性價比試算與評價分級
    sample.js       範例資料產生器
  server/         Apps Script 伺服器端（.gs）
    Main.gs         選單、Web App 進入點、HTML 組裝
    Api.gs          前端唯一會呼叫的一層
    Store.gs        試算表存取
  ui/             前端
    Index.html      版面骨架
    styles.html     設計系統
    app.html        介面邏輯
    bridge.html     google.script.run 的 Promise 包裝
tools/
  build.js        src/ → dist/（clasp push 用）
  preview.js      src/ → dist-preview/index.html（離線版）
  mock-backend.js 離線版的假後端
test/
  solver.test.js  16 項演算法測試
```

### 為什麼需要建置步驟

`src/lib/` 的演算法必須同時跑在三個地方：Apps Script 伺服器端（`.gs`）、
瀏覽器前端（包在 `<script>` 裡的 `.html`）、以及 node 測試。
與其複製三份，不如留一份原始碼，建置時各自產生。

測試用 `vm` 把所有 lib 檔案跑在**同一個 context** 裡 ——
和它們在 Apps Script 與瀏覽器裡「共用同一個全域範圍」的方式完全一致，
所以測試環境就是正式環境。
