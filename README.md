# War Robots 禮包比價與基準單價推算

給手遊《War Robots》玩家用的商城禮包比價工具。記錄你看過的禮包（售價 + 內容物），
它會自動反解出每一種物品的「基準單價」，然後告訴你新看到的禮包到底值不值得買。

網站放在 **GitHub Pages**，資料存在 **你自己的 Google 試算表**。

---

## 它在解什麼問題

商城從來不會告訴你「1 顆金幣值多少錢」。但每一筆禮包其實都是一條方程式：

```
售價 ≈ 數量₁ × 單價₁ + 數量₂ × 單價₂ + …
```

記了十幾筆之後，這些方程式疊起來就是一個超定線性系統，可以把單價解出來。
單價不可能是負數，所以用**帶 ridge 正則化的非負最小平方（NNLS）**求解。

實作上有三個關鍵處理，少一個結果就會歪掉：

| 處理 | 為什麼需要 |
|---|---|
| **相對誤差加權** | 直接對「元」做最小平方的話，一筆 3290 元的禮包會壓過十筆 90 元的。每列除以該包售價後，貴包便宜包才有同等發言權。 |
| **欄位正規化** | 銀幣一次給 250 萬、終極資料卡一次給 1 張，量級差了八個數量級。把每個欄位縮成單位長度求解，最後再還原。 |
| **Bootstrap 區間** | 只出現在一兩包裡的稀有物品，點估計幾乎沒有意義。重抽禮包重解 240 次，用分位數給出「可能區間」而不是一個假裝很確定的數字。 |

推算引擎整個跑在**瀏覽器裡**，所以改一個數字立刻重算，不必等伺服器。
Apps Script 只負責試算表的讀寫。

## 兩種使用方式

**本機模式（打開就能用）**
什麼都不用設定，直接開網站就能記錄、看單價、試算。資料存在那台裝置的瀏覽器裡。
缺點是換一台裝置就看不到。

**連接試算表（推薦）**
資料改存在你的 Google 試算表，手機電腦同步，也能直接在試算表上編輯。
需要一次性的設定，大約 5 分鐘，步驟在下面。

可以先用本機模式，之後再連接 —— 連上後可以把本機累積的資料一鍵搬上去。

---

## 設定試算表（只要做一次）

### 步驟 1：建立試算表

開一個新的 Google 試算表，取名例如「War Robots 禮包」。

從網址列抄下中間那一長串，等一下要用：

```
https://docs.google.com/spreadsheets/d/【就是這一段，抄下來】/edit
```

### 步驟 2：貼上程式

1. 在試算表選單點 **擴充功能 → Apps Script**
2. 把編輯器裡原本的 `function myFunction() {}` 全部刪掉
3. 打開這個專案的 [`dist-gas/Code.gs`](dist-gas/Code.gs)，**全選複製**，貼進去
4. 找到最上面的 `CONFIG`，改這兩行：

```js
var CONFIG = {
  TOKEN: '換成你自己的密碼',        // ← 自己想一組密碼，越長越好
  SHEET_ID: '換成你的試算表 ID'      // ← 貼上步驟 1 抄的那一段
};
```

5. 按存檔（Ctrl/Cmd + S）

> 密碼不會進 GitHub，只存在你的 Apps Script 專案和你自己的瀏覽器裡。

### 步驟 3：部署

在 Apps Script 編輯器右上角：**部署 → 新增部署作業**

- 類型（齒輪圖示）：**網頁應用程式**
- 執行身分：**我**
- **誰可以存取：所有人** ← 這個一定要選「所有人」

按「部署」，第一次會要求授權（出現「Google 尚未驗證這個應用程式」是正常的，
點「進階」→「前往…（不安全）」繼續，因為這就是你自己剛寫的程式）。

完成後會給你一個網址，長得像：

```
https://script.google.com/macros/s/AKfycb…/exec
```

**把它複製起來。**

### 步驟 4：在網站上連接

打開網站 → **設定** 分頁 → **連接 Google 試算表** → 貼上網址和密碼 → **測試並連接**。

連上之後，試算表裡會自動長出四張工作表：

| 工作表 | 內容 |
|---|---|
| `禮包` | 你的禮包紀錄。每個物品一欄，可以直接在試算表上編輯。 |
| `單價看板` | 算出來的基準單價、區間、信心度。最後一欄 `鎖定單價` 是**你可以填的輸入**。 |
| `設定` | 推算參數。 |
| `試算紀錄` | 你按「存進試算紀錄」時累積的結果。 |

### 之後改程式怎麼辦？

**網站的部分不用管** —— 只要 `main` 有新的 commit，GitHub Actions 就會自動重新部署。

**`Code.gs` 只有在它本身改動時才需要重貼**（很少發生）。真的要重貼的話：
複製新的 `dist-gas/Code.gs` 蓋掉舊的、重填 `CONFIG` 那兩行、然後
**部署 → 管理部署作業 → 編輯（鉛筆）→ 版本選「新版本」→ 部署**。
這樣網址不會變，網站那邊不用重新連接。

## 網站部署

不用手動設定。推到 `main` 之後，`.github/workflows/deploy.yml` 會：

1. 跑演算法測試（不過就不部署）
2. 建置 `dist-web/`
3. 自動開啟這個 repo 的 Pages（`configure-pages` 的 `enablement`）並發佈

網址是：

```
https://<你的帳號>.github.io/war-robots-pricing-engine/
```

> 測試指令用 `npm test`，不要改成 `node --test 'test/*.test.js'`。
> 加引號等於要 node 自己展開萬用字元，那是 Node 22 起才有的行為，
> 舊版會把整串當成真實檔名然後找不到。交給 shell 展開就沒有版本問題。

手機上用 Safari／Chrome 開這個網址，「加入主畫面」就跟原生 App 一樣。

## 怎麼用

### 記錄禮包
「禮包」分頁 → 新增。物品點丸子選，數量和售價用數字鍵盤（電腦上也可以直接打實體鍵盤）。

### 從截圖批次新增（不用一筆一筆打）

一筆一筆輸入太慢的話，走這條：

1. 在遊戲裡截下商城畫面
2. 到 **設定 → 從截圖批次新增 → 複製辨識提示詞**
3. 把提示詞連同截圖丟給任何看得懂圖的 AI
4. 把它產出的 JSON 整段貼回來 → **檢查** → **匯入**

提示詞全文在 [`docs/辨識提示詞.md`](docs/辨識提示詞.md)。

**它刻意要求 AI 認不出來就說認不出來。** 漏掉一項物品不是「少一點」而已 ——
那一項的價值會被攤到同一包的其他物品上，整組單價跟著歪掉，而且從結果完全看不出哪裡錯。
所以含有未辨識內容的禮包會被自動標成「不納入推算」，等你補上正確物品再打開。

機器人、機師、武器、無人機這類東西目前不在物品清單裡，也會走同一條路。

匯入前會先檢查一次：任何一筆有問題都會指出是第幾筆、哪裡有問題，而且整筆不會被匯入。
**設定 → 匯出成 JSON** 則可以把現有資料倒出來備份，格式跟匯入完全相同。

### 看單價
「看板」分頁。每一列是一種物品：

- **大數字** 是基準單價，以該物品的「計價單位」計價 —— 銀幣一枚值 0.0000022 元這種
  數字讀不動，所以銀幣看「每 1M」、金幣看「每 1K」、鑰匙看「每 10K」、資料卡看「每張」。
  推算引擎內部一律用每 1 單位的原始值，換算只發生在畫面上與試算表裡
- **淺色橫條** 是 80% 可能區間，中間的直線是點估計。橫條越寬代表越不確定
- **信心度標籤** 綜合「出現在幾包裡」和「區間有多寬」
- 只出現在 1 包裡、或被解成 0 的物品，會直接寫明原因，不會假裝那是行情

橫條的橫軸是「相對於這個物品自己的點估計，從 0 到 2 倍」——
所以銀幣和終極資料卡雖然差了八個數量級，還是能在同一個看板上比較「有多不確定」。

### 試算新禮包
「試算」分頁，輸入售價和內容物，會即時算出：

- **性價比指數** = 理論價值 ÷ 售價，以及它自己的可能區間
- **評價**（超值 / 划算 / 正常行情 / 偏貴 / 很貴）
- 這包在你記錄過的所有禮包裡排第幾
- 價值是由哪些物品撐起來的

「正常行情」的寬度不是拍腦袋訂的，而是**跟著模型自己的平均誤差走**。
如果模型連歷史禮包都有 15% 的誤差，那 1.10 倍就分辨不出是划算還是雜訊，不該說它超值。

### 鎖定單價（讓結果收斂最有效的手段）
「設定」分頁，對任何物品填入你有把握的單價，它就會被當成已知值從售價裡先扣掉，
其餘物品再去解剩下的部分。稀有物品估不準的時候，先鎖幾個你確定的常見物品，
整體結果會立刻穩下來。

## 常見狀況

**連接時說「收到的不是預期的回應」**
部署時「誰可以存取」沒有選「所有人」。回 Apps Script 改掉，然後**重新部署**（要選「新版本」）。

**連接時說「連不上 Apps Script」**
網址貼錯，或是改了程式之後沒有重新部署。網址結尾必須是 `/exec`，不是 `/dev`。

**「有物品被解成 0 元」**
代表它在資料裡總是跟別的東西綁在一起出現，方程式分不出它自己的貢獻。
記一筆「只含它」或「搭配組合不同」的禮包就會解開。

**「待解物品比禮包筆數還多」**
方程式不夠。繼續累積禮包，或鎖定幾個有把握的單價。

**「某個物品的區間寬得離譜」**
它出現的次數太少，或總是和另一個物品等比例出現（共線）。這是誠實的結果，不是 bug。

**手動改了試算表之後網站沒更新**
重新整理網頁即可。連上之後，資料的唯一真實來源就是試算表。

## 安全性

網站放在 GitHub Pages 是公開的，但裡面**沒有任何資料，也沒有密碼**。

Apps Script 的網址必須開放給「所有人」，因為瀏覽器從 GitHub Pages
跨網域打過去時，Google 不允許帶著你的登入身分。擋在前面的是密碼：
每個請求都要附上正確的 `TOKEN`，否則直接回絕。

- 密碼存在你的 Apps Script 專案（`CONFIG.TOKEN`）和你自己瀏覽器的 localStorage
- 兩邊都不會進 GitHub
- 比對密碼時跑固定圈數，不會因為前幾個字對了就比較慢（避免被一個字一個字試出來）
- 想換密碼：改 `CONFIG.TOKEN`、重新部署、在網站上重新連接一次

如果你不想開放「所有人」，那就只能用本機模式，或改回「整個 App 裝在 Apps Script 裡」
的做法（那樣就沒有 GitHub Pages，每次改動都得手動更新 Apps Script）。

## 開發

```bash
npm test              # 演算法測試（node --test，零相依套件）
node tools/build.js   # 產生 dist-web/ 與 dist-gas/
node tools/build.js --serve   # 建置並起一個本機伺服器
```

### 專案結構

```
src/
  lib/            純 JS 演算法，同時被三個環境載入
    catalog.js      物品目錄、數字格式化
    linalg.js       NNLS、Cholesky、bootstrap 亂數
    solver.js       基準單價推算引擎
    evaluate.js     性價比試算與評價分級
    sample.js       範例資料產生器
    importer.js     JSON 批次匯入解析與驗證
    prompt.js       給別的 AI 看截圖用的提示詞
  gas/
    Code.gs         Apps Script 資料層（試算表的 JSON API）
  ui/
    index.html      版面骨架
    styles.html     設計系統
    app.html        介面邏輯
    bridge.html     資料層：本機 / 試算表兩種模式
tools/
  build.js        → dist-web/index.html（網站）+ dist-gas/Code.gs（貼進 Apps Script）
test/
  solver.test.js    演算法測試
  display.test.js   計價單位換算測試
  importer.test.js  匯入解析測試
.github/workflows/
  deploy.yml      推到 main → 跑測試 → 部署 GitHub Pages
```

### 為什麼需要建置步驟

`src/lib/` 的演算法要同時跑在瀏覽器、Apps Script 和 node 測試裡。
與其複製三份，不如留一份原始碼，建置時各自產生。
`catalog.js` 兩邊都要用 —— 試算表的欄位標題就是從它來的，
所以它會被接在 `Code.gs` 前面一起輸出。

建置時會把產生出來的每個 `<script>` 區塊都拿去解析一次。
漏掉一個 `</script>` 是靜默失敗：檔案照樣產生，但整個 app 不會跑。

測試用 `vm` 把所有 lib 檔案跑在**同一個 context** 裡 ——
和它們在 Apps Script 與瀏覽器裡「共用同一個全域範圍」的方式完全一致，
所以測試環境就是正式環境。
