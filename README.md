# War Robots 禮包比價與基準單價推算

給手遊《War Robots》玩家用的商城禮包比價工具。記錄你看過的禮包（售價 + 內容物），
它會自動反解出每一種物品的「基準單價」，然後告訴你新看到的禮包到底值不值得買。

網站放在 **GitHub Pages**，資料存在 **你自己的 Google 試算表**。

---

## 它在解什麼問題

商城從來不會告訴你「1 顆金幣值多少錢」。但每一筆禮包其實都是一條方程式：

```
售價 ≈ 數量₁ × 單價₁ + 數量₂ × 單價₂ + …
```

記了十幾筆之後，這些方程式疊起來就是一個超定線性系統，可以把單價解出來。
單價不可能是負數，所以用**帶 ridge 正則化的非負最小平方（NNLS）**求解。

實作上有三個關鍵處理，少一個結果就會歪掉：

| 處理 | 為什麼需要 |
|---|---|
| **相對誤差加權** | 直接對「元」做最小平方的話，一筆 3290 元的禮包會壓過十筆 90 元的。每列除以該包售價後，貴包便宜包才有同等發言權。 |
| **欄位正規化** | 銀幣一次給 250 萬、終極資料卡一次給 1 張，量級差了八個數量級。把每個欄位縮成單位長度求解，最後再還原。 |
| **Bootstrap 區間** | 只出現在一兩包裡的稀有物品，點估計幾乎沒有意義。重抽禮包重解 240 次，用分位數給出「可能區間」而不是一個假裝很確定的數字。 |

推算引擎整個跑在**瀏覽器裡**，所以改一個數字立刻重算，不必等伺服器。
Apps Script 只負責試算表的讀寫。

---

## 兩種使用方式

**本機模式（打開就能用）**
什麼都不用設定，直接開網站就能記錄、看單價、試算。資料存在那台裝置的瀏覽器裡。
缺點是換一台裝置就看不到。

**連接試算表（推薦）**
資料改存在你的 Google 試算表，手機電腦同步，也能直接在試算表上編輯。
需要一次性的設定，大約 5 分鐘，步驟在下面。

可以先用本機模式，之後再連接 —— 連上後可以把本機累積的資料一鍵搬上去。

---

## 設定試算表（只要做一次）

### 步驟 1：建立試算表

開一個新的 Google 試算表，取名例如「War Robots 禮包」。

從網址列抄下中間那一長串，等一下要用：

```
https://docs.google.com/spreadsheets/d/【就是這一段，抄下來】/edit
```

### 步驟 2：貼上程式

1. 在試算表選單點 **擴充功能 → Apps Script**
2. 把編輯器裡原本的 `function myFunction() {}` 全部刪掉
3. 打開這個專案的 [`dist-gas/Code.gs`](dist-gas/Code.gs)，**全選複製**，貼進去
4. 找到最上面的 `CONFIG`，改這兩行：

```js
var CONFIG = {
  TOKEN: '換成你自己的密碼',        // ← 自己想一組密碼，越長越好
  SHEET_ID: '換成你的試算表 ID'      // ← 貼上步驟 1 抄的那一段
};
```

5. 按存檔（Ctrl/Cmd + S）

> 密碼不會進 GitHub，只存在你的 Apps Script 專案和你自己的瀏覽器裡。

### 步驟 3：部署

在 Apps Script 編輯器右上角：**部署 → 新增部署作業**

- 類型（齒輪圖示）：**網頁應用程式**
- 執行身分：**我**
- **誰可以存取：所有人** ← 這個一定要選「所有人」

按「部署」，第一次會要求授權（出現「Google 尚未驗證這個應用程式」是正常的，
點「進階」→「前往…（不安全）」繼續，因為這就是你自己剛寫的程式）。

完成後會給你一個網址，長得像：

```
https://script.google.com/macros/s/AKfycb…/exec
```

**把它複製起來。**

### 步驟 4：在網站上連接

打開網站 → **設定** 分頁 → **連接 Google 試算表** → 貼上網址和密碼 → **測試並連接**。

連上之後，試算表裡會自動長出四張工作表：

| 工作表 | 內容 |
|---|---|
| `禮包` | 你的禮包紀錄。每個物品一欄，可以直接在試算表上編輯。 |
| `單價看板` | 算出來的基準單價、區間、信心度。最後一欄 `參考單價` 是**你可以填的輸入**。 |
| `設定` | 推算參數。 |
| `試算紀錄` | 你按「存進試算紀錄」時累積的結果。 |

### 換到手機上（不用手打那串網址）

在已經連好的電腦上：**設定 → 複製「在手機上開啟」的連結**，
把連結傳給自己（例如自己的 LINE 記事本），用手機打開就自動連上同一份試算表。

連線設定放在網址 `#` 之後，那一段瀏覽器永遠不會送到伺服器，所以不會留在任何
存取紀錄裡；網站讀完也會立刻把它從網址列抹掉，不會留在瀏覽紀錄。
但它確實含有你的密碼，**只傳給自己**。

在別台裝置改過資料之後，按 **設定 → 從試算表重新讀取** 就會抓到最新的。

### 之後改程式怎麼辦？

**網站的部分不用管** —— 只要 `main` 有新的 commit，GitHub Actions 就會自動重新部署。

**`Code.gs` 只有在它本身改動時才需要重貼**（很少發生）。真的要重貼的話：
複製新的 `dist-gas/Code.gs` 蓋掉舊的、重填 `CONFIG` 那兩行、然後
**部署 → 管理部署作業 → 編輯（鉛筆）→ 版本選「新版本」→ 部署**。
這樣網址不會變，網站那邊不用重新連接。

不用手動設定。推到 `main` 之後，`.github/workflows/deploy.yml` 會：

1. 跑演算法測試（不過就不部署）
2. 建置 `dist-web/`
3. 自動開啟這個 repo 的 Pages（`configure-pages` 的 `enablement`）並發佈

網址是：

```
https://<你的帳號>.github.io/war-robots-pricing-engine/
```

> 測試指令用 `npm test`，不要改成 `node --test 'test/*.test.js'`。
> 加引號等於要 node 自己展開萬用字元，那是 Node 22 起才有的行為，

手機上用 Safari／Chrome 開這個網址，「加入主畫面」就跟原生 App 一樣。

## 怎麼用

### 記錄禮包
「禮包」分頁 → 新增。編輯器是**整頁一次到底**：售價、已加的物品、物品丸子、
數字鍵盤全部在同一個畫面上，從頭到尾不會有東西彈出來又消失。

- 一打開焦點就在**售價**，可以直接開始打
- 點一下物品丸子 → 加進來並立刻成為輸入目標，接著打數量就好
- 鍵盤上方的快捷值會跟著目前在打哪一格變
- 內容物那一格會**即時顯示理論價值與性價比**，邊記就邊知道這包划不划算
- 名稱可以完全不填，留空會用內容物自動命名
- 物品丸子預設只放 **12 個常用的**（金卡、泰坦、終極收在「更多」裡）
- **銀幣以 M 為單位輸入** —— 遊戲本身就顯示「474.7 M」，要人打 474700000 太荒謬。
  選到銀幣時鍵盤的 `000` 會換成小數點，打 `2.5` 就是 250 萬。
  存進試算表與送進引擎的一律是原始數量，M 只是輸入介面的事

### 找以前記過的禮包

「禮包」分頁最上面是篩選列。點物品丸子就只留**同時包含**這些物品的禮包 ——
用 AND 而不是 OR，因為這個功能的實際用途是「我想看以前有沒有出過類似的包」：
選了白金又選了金幣，要找的是兩者都有的組合包，不是兩者任一。

丸子上的小數字是該物品出現在幾筆禮包裡，而且只列出真的出現過的物品。
排序可以切「最新 / 售價 / 性價比」——
切到性價比就能一眼看出你記錄過的哪幾包最划算。

### 從截圖批次新增（不用一筆一筆打）

一筆一筆輸入太慢的話，走這條：

1. 在遊戲裡截下商城畫面
2. 到 **設定 → 從截圖批次新增 → 複製辨識提示詞**
3. 把提示詞連同截圖丟給任何看得懂圖的 AI
4. 把它產出的 JSON 整段貼回來 → **檢查** → **匯入**

提示詞全文在 [`docs/辨識提示詞.md`](docs/辨識提示詞.md)。

**它刻意要求 AI 認不出來就說認不出來。** 漏掉一項物品不是「少一點」而已 ——
那一項的價值會被攤到同一包的其他物品上，整組單價跟著歪掉，而且從結果完全看不出哪裡錯。
所以含有未辨識內容的禮包會被自動標成「不納入推算」，等你補上正確物品再打開。

機器人、機師、武器、無人機這類東西目前不在物品清單裡，也會走同一條路。

匯入前會先檢查一次：任何一筆有問題都會指出是第幾筆、哪裡有問題，而且整筆不會被匯入。
**設定 → 匯出成 JSON** 則可以把現有資料倒出來備份，格式跟匯入完全相同。

### 看單價
「看板」分頁。每一列是一種物品：

- **大數字** 是基準單價，以該物品的「計價單位」計價。銀幣一枚值 0.0000022 元這種
  數字讀不動，所以每個物品都配一個計價單位，讓金額盡量落在 **1～10 元**：
  銀幣每 1M，金幣／鑰匙／電池每 1K，白金與機師晶片每 100，模塊與微晶片每 10。
  這些值是用 96 筆實際資料校準的 —— 白金與微晶片原本都設成每 1K，換算後會
  變成 95 元與 210 元，完全違背這個設計的初衷。
  資料卡與升級代幣停在「每 1 張／個」—— 它們一單位就值好幾十塊，而且買不到半張。
  推算引擎內部一律用每 1 單位的原始值，換算只發生在畫面上與試算表裡
- **淺色橫條** 是 80% 可能區間，中間的直線是點估計。橫條越寬代表越不確定
- **信心度標籤** 綜合「出現在幾包裡」和「區間有多寬」
- 只出現在 1 包裡、或被解成 0 的物品，會直接寫明原因，不會假裝那是行情

橫條的橫軸是「相對於這個物品自己的點估計，從 0 到 2 倍」——
所以銀幣和終極資料卡雖然差了八個數量級，還是能在同一個看板上比較「有多不確定」。

### 試算新禮包
「試算」分頁，輸入售價和內容物，會即時算出：

- **性價比指數** = 理論價值 ÷ 售價，以及它自己的可能區間
- **評價**（超值 / 划算 / 正常行情 / 偏貴 / 很貴）
- 這包在你記錄過的所有禮包裡排第幾
- 價值是由哪些物品撐起來的

「正常行情」的寬度不是拍腦袋訂的，而是**跟著模型自己的平均誤差走**。
如果模型連歷史禮包都有 15% 的誤差，那 1.10 倍就分辨不出是划算還是雜訊，不該說它超值。

### 參考單價（不是鎖定）

有些物品在每一包裡都綁在一起賣 —— 例如每包都是「金幣 + 銀幣」且比例固定。
這時方程式只說得出「金幣單價 + 1000 × 銀幣單價 = 某數」，兩者怎麼分攤都是誤差 0 的
合法解，**最佳化本身挑不出來**。正則化就是在這時候當裁判。

預設的裁判標準是「誰比較接近 0 就選誰」—— 那只是數學上方便，沒有道理。
在「設定」填了參考單價之後，標準改成「誰比較接近你的猜測就選誰」：

```
最小化   誤差²  +  λ · ‖單價 − 參考值‖²
```

**λ 的單位是「相當於幾筆禮包」**，預設 1。拉力正好是 `份量 / (出現包數 + 份量)`：

| 該物品出現在幾包 | 參考值的份量 |
|---|---|
| 1 包 | 50% |
| 4 包 | 20% |
| 20 包 | 5% |

所以這**不是鎖定**：禮包記得越多，你的猜測就越沒有影響力，填錯了也會被資料自己修正。

**而且它會自動退場。** 某個物品一旦累積到足夠的「有效觀測次數」，它的參考值就整個停用，
影響歸零 —— 不是「變得很小」而是真的 0，結果與從未給過參考值完全相同。
設定頁會直接寫「已自動退場，完全由資料決定」。

### 有效觀測次數：為什麼記了 30 包還是不準

判斷「資料夠不夠」用的不是出現包數，而是**有效觀測次數**。

如果金幣與銀幣在每一包裡都是固定比例，那記 30 包和記 1 包提供的資訊一樣多 ——
方程式永遠只說得出兩者的組合值。這時有效觀測次數會是 **0.02 次**，不是 30 次。

```
共線 30 包：   出現 30 包 → 有效觀測 0.02 次
獨立 12 包：   出現 12 包 → 有效觀測 12.01 次
```

算法是 `1 / (GG⁻¹)ⱼⱼ`（G 是正規方程式矩陣）—— 欄位彼此正交時它就等於出現次數，
一旦共線就大幅下降。看板遇到這種物品會直接寫「但有效觀測只有 0.0 次」並告訴你
該記什麼樣的禮包才解得開。

> 順帶一提：**不能用 bootstrap 區間來判斷這件事。** 共線時每次重抽都收斂到同一個
> 最小範數解，區間反而很窄 —— 但那個穩定是假的，它只是穩定在一個任意的答案上。

代價要講清楚：資料本來就夠的地方，參考值會把答案拉偏一點，而且會透過物品之間的
相關性波及到沒給參考值的物品。所以預設份量只給「一筆」，並且會自動退場。

### 三種算法

看板一次只用一種（設定裡可以換，預設是穩健回歸），但試算頁可以把四種並排比較。

| | 它在做什麼 | 什麼時候有差 |
|---|---|---|
| **最小平方** | 教科書解法，所有禮包一視同仁 | 資料乾淨時跟穩健回歸幾乎一樣 |
| **穩健回歸**（預設） | 偏離行情太遠的禮包自動降權 | 有人打錯數字、或遇到真的超級促銷時 |
| **完整貝氏** | Gibbs 抽樣截斷多元常態後驗 | 點估計差不多，**差別在區間** |
| **參考值優先**（只在試算頁） | 把你填的參考單價當定值 | 想知道「照我自己的價目表這包值多少」 |

**穩健回歸實際擋掉了什麼。** 12 筆禮包裡把其中一筆的售價少打一個 0：

```
最小平方   平均誤差 52.8%      ← 一筆打錯就毀掉整張看板
穩健回歸   平均誤差  0.6%      ← 只有那一筆被標成「採信 0%」
```

這件事比想像中難做對，過程中踩到四個坑，每一個都寫成了測試：

1. **IRLS 不能每輪重估尺度，會塌掉。** 降權 → 殘差變小 → 尺度變小 → 門檻變嚴
   → 更多列被降權 → 再循環。用 96 筆真實資料實測，尺度從 11% 一路掉到 1%，
   門檻從 51% 收到 5%，最後宣稱 62 筆裡有 17 筆是離群值 —— 包括只偏離 **2%**
   的那些。這是 redescending M-estimator 的已知性質，標準解法（MM 估計）就是
   **尺度先定好、IRLS 過程中不再更新**。

2. **只用 Huber 沒有用。** 少打一個 0 的禮包數量通常也很大，槓桿足以把迴歸線拉到
   自己身上，於是**它的殘差變小，反而是誠實的禮包看起來像離群值**。所以要先做一輪
   「逐筆剔除」—— 讓每筆禮包由不含它自己的模型來評斷，它就遮掩不了自己。
3. **逐筆剔除的守門條件不能用「出現過幾次」。** 商城裡大量是單品包，很多物品只被
   一兩筆釘住，拿掉那一筆之後模型根本無從預測它。用計次判準的那一版，
   把真實資料的擬合誤差從 0.8% 炸到 **1000% 以上**。
4. **算槓桿值時必須關掉相對誤差加權**，否則售價打錯的那列權重會變成十倍，
   槓桿值衝到 1，反而被當成「無從評斷」而跳過篩檢 —— 正好逃掉。

最後的判準是「偏離要超過 50% 才算大錯」：篩檢只抓少打一個 0 這種等級的問題，
一般的離群（促銷、模型本身的誤差）交給後面的 Tukey bisquare 重新加權處理。

**完整貝氏是為了區間而存在的**，不是為了更準。同一批共線資料：

```
bootstrap 區間寬度   2%      ← 假的。每次重抽都收斂到同一個最小範數解
後驗區間寬度        43%      ← 誠實的。資料分不出來，它就說分不出來
```

所以試算頁看到「完整貝氏的區間比其他三個寬很多」時，不是它算得比較差，
而是另外三個低估了不確定性。

### 兩種基準：「最好價格」與「平均行情」

同一個物品常常有好幾種賣法，於是「基準單價」有兩種都合理、但意義完全不同的算法。
看板最上面可以直接切換，而且每一列都會把**另一種口徑的數字並排寫出來**：

| | 怎麼算 | 這包「划算」是什麼意思 |
|---|---|---|
| **最好價格** | 同物品只採用最便宜的那種賣法 | 比你買得到的最低價還便宜 |
| **平均行情** | 所有報價都算數，包括比較貴的小包 | 比商城平均而言便宜 |

```
白金 1000 賣 100 元   → 每單位 0.100   最好價格：不納入（沒有人會買它）
白金 1500 賣 130 元   → 每單位 0.087   最好價格：這個才算數
```

「最好價格」只對**純單品**適用。組合包的單價沒有被直接觀測到，兩包之間沒有可以
直接比較的單價，所以組合包永遠不會被排除。被排除的禮包紀錄完整保留，在清單上
標「未納入推算 · 有更便宜的『⋯』」，一眼就看得出哪個才該買。

實際差多少：同一批 96 筆資料，「最好價格」納入 51 筆、平均誤差 11.9%；
「平均行情」納入 81 筆、平均誤差 13.6%。金幣分別是 4.71 與 4.50 元/1K。

### 完全重複的紀錄會自動合併

同一個禮包在商城的不同分頁各出現一次，很自然會被記成兩筆。但那是**同一個報價
被看到兩次**，不是兩次獨立觀測 —— 兩筆一模一樣的紀錄在數學上就是同一條方程式，
放兩次只會讓它的權重變成兩倍，連帶「出現在幾包」與有效觀測次數也跟著虛胖，
看板上的信心度因此高估。

所以售價與內容物都相同的紀錄會自動合併成一次觀測（日期不納入比對 —— 售價完全
一樣的話，那不是「再量一次」而是同一個報價）。設定頁另外有一鍵清掉多餘紀錄的
按鈕，每組保留最早的那一筆。

> 實測：96 筆裡有 15 組重複。合併後資料卡·基礎銀從「出現 3 包」修正為 2 包，
> 信心度也從「中」降為「低」—— 那才是實際的證據量。

### 資料健檢：自動抓出可能打錯的那幾筆

資料主要來自 AI 看截圖辨識，最常見的錯就是**數量少看一位**。而同一種資料卡
不論幾張一包，每張的價格其實非常一致，所以只要比對「同物品的其他單品包」
就抓得出來：

```
武器銀 ×5   NT$ 33  → 6.60 元/張
武器銀 ×10  NT$ 66  → 6.60 元/張
武器銀 ×15  NT$ 99  → 6.60 元/張
武器銀 ×50  NT$330  → 6.60 元/張
武器銀 ×7   NT$ 99  → 14.14 元/張   ← 幾乎確定是把 15 看成 7
```

超過同物品中位數 1.5 倍的會在禮包清單上標「可能打錯了」，並寫出你自己記過
的正常價格。用中位數而不是平均，否則離群值會把基準自己拉高，然後它就不離群了。

只看純單品，而且同物品至少要有三筆 —— 兩筆不一致的時候無從得知誰才是對的。

### 自由度：為什麼有時候誤差 0.8% 反而不是好消息

待解物品有 11 種、納入計算的禮包只有 12 筆時，**解必定幾乎完美通過每一個點**。
那不是模型準，是它還沒被考驗過。這種情況下看板會直接寫「平均誤差：尚不算數」，
性價比的「正常行情」區間也會改用比較保守的寬度，而不是拿一個假的小誤差去當標準。

## 常見狀況

**連接時說「收到的不是預期的回應」**
部署時「誰可以存取」沒有選「所有人」。回 Apps Script 改掉，然後**重新部署**（要選「新版本」）。

**連接時說「連不上 Apps Script」**
網址貼錯，或是改了程式之後沒有重新部署。網址結尾必須是 `/exec`，不是 `/dev`。

**「有物品被解成 0 元」**
代表它在資料裡總是跟別的東西綁在一起出現，方程式分不出它自己的貢獻。
記一筆「只含它」或「搭配組合不同」的禮包就會解開。

**「待解物品比禮包筆數還多」**
方程式不夠。繼續累積禮包，或給幾個參考單價當起點。

**「某個物品的區間寬得離譜」**
它出現的次數太少，或總是和另一個物品等比例出現（共線）。這是誠實的結果，不是 bug。

**手動改了試算表之後網站沒更新**
重新整理網頁即可。連上之後，資料的唯一真實來源就是試算表。

## 安全性

網站放在 GitHub Pages 是公開的，但裡面**沒有任何資料，也沒有密碼**。

Apps Script 的網址必須開放給「所有人」，因為瀏覽器從 GitHub Pages
跨網域打過去時，Google 不允許帶著你的登入身分。擋在前面的是密碼：
每個請求都要附上正確的 `TOKEN`，否則直接回絕。

- 密碼存在你的 Apps Script 專案（`CONFIG.TOKEN`）和你自己瀏覽器的 localStorage
- 兩邊都不會進 GitHub
- 比對密碼時跑固定圈數，不會因為前幾個字對了就比較慢（避免被一個字一個字試出來）
- 想換密碼：改 `CONFIG.TOKEN`、重新部署、在網站上重新連接一次

如果你不想開放「所有人」，那就只能用本機模式，或改回「整個 App 裝在 Apps Script 裡」
的做法（那樣就沒有 GitHub Pages，每次改動都得手動更新 Apps Script）。

### 為什麼需要建置步驟

`src/lib/` 的演算法要同時跑在瀏覽器、Apps Script 和 node 測試裡。
與其複製三份，不如留一份原始碼，建置時各自產生。
`catalog.js` 兩邊都要用 —— 試算表的欄位標題就是從它來的，
所以它會被接在 `Code.gs` 前面一起輸出。

建置時會把產生出來的每個 `<script>` 區塊都拿去解析一次。
漏掉一個 `</script>` 是靜默失敗：檔案照樣產生，但整個 app 不會跑。

測試用 `vm` 把所有 lib 檔案跑在**同一個 context** 裡 ——
和它們在 Apps Script 與瀏覽器裡「共用同一個全域範圍」的方式完全一致，
所以測試環境就是正式環境。
